MUGENのSFalseとbottomとは？評価不能（エラー）時の挙動・警告・WinMUGEN/1.0/Ikemen GO差分まとめ

MUGENのCNS/CMD式は「整数/実数の計算」だけでなく、トリガの参照（helper/target等のリダイレクト）や数学関数も含みます。 その結果、実行時に 評価不能（回復不能エラー） が起きることがあります。 このとき登場するのが、旧系の SFalse と、MUGEN 1.0+ 系の bottom です。

結論（運用上の要点）

  • SFalse（旧）：評価不能を「SC false」という特殊な偽値として扱い、式評価を継続するための仕組み。
  • bottom（1.0+）：評価不能を表す“値”として導入された仕組み。式のどこかで発生すると原則として式全体に伝播（ただしIfElse/Condは例外）。
  • 安全策：無効リダイレクト（helper/target不在）や定義域違反が起きうる式は、存在確認→参照の順に書く。必要ならCondで危険式を未評価化する。
  • Ikemen GO：少なくとも一部バージョンで、無効リダイレクトが「bottom相当」ではなく「0扱い」で比較に入る挙動が報告されており、MUGENコードの前提が崩れる可能性がある（後述）。

1. 用語整理：SFalseとbottomは「何を解決するための仕組み」か

SFalse（SC values / Short-Circuit values：旧系）

旧系の式仕様（WinMUGEN世代のexp.doc系）では、評価不能（例：0除算、負数平方根、存在しない対象へのリダイレクト）に遭遇したとき、 その場でクラッシュさせず式評価を“完了させる”ために SC値（STrue / SFalse） を用いる、と説明されています。 SFalseは「エラー起因の偽」として扱われ、以後の演算の結果にも影響します。

bottom（MUGEN 1.0+ の「回復不能エラー値」）

MUGEN 1.0+ では、評価不能を表す値として bottom が明示されます。 代表的な原因は、0除算、負数平方根、無効なトリガリダイレクトです。 bottomが式中に出現した場合、原則として式全体がbottomになります（例外：IfElse/Cond）。 また、Condition-type trigger（trigger行の条件式）はbottomを0として扱うため、エラー式でtriggerが暴発しない設計になっています。

2. 生成原因（網羅カテゴリ）と「どのエンジンで何になるか」

ここでは「特定トリガ個別」ではなく、評価不能を生む根本カテゴリで網羅します（実運用ではこの粒度が最も再現性が高い）。

評価不能の根本カテゴリ 典型例（式） WinMUGEN/旧仕様の見え方 MUGEN 1.0+ の見え方 備考（伝播・注意点）
0除算 1.0 / time（time=0） SFalse（SC false）になり得る bottom 多くの場合、警告が出る。IfElseは未使用分岐でも評価して警告が出得る。Condで回避可能。
数学関数の定義域違反（負数平方根など） fvar(0) ** 0.5（fvar(0)=-1） SFalse（SC false）になり得る bottom 1.0+ではbottomが式全体へ伝播しやすい（IfElse/Condを除く）。
数学関数の定義域違反（逆三角・対数など） acos(2) / ln(0) など SFalse（または0相当）になり得る bottom（多くの数学トリガは明示的にbottomを返す） 「関数のError conditions」に該当。
無効リダイレクト（helper/target/parent等の不在参照） helper(1234), life（helper不在） エラー（旧仕様ではSFalseに落ちる/偽扱いになる前提で書かれがち） bottom（無効リダイレクトはbottomを返す） Condition-type triggerではbottomは0扱い＝発火しない。ただし「比較式の形」次第でエンジン差が出やすい（Ikemen注意）。

“bottom/SFalseを返すトリガ”をさらに演算する abs(bottom) / tan(bottom) など SFalseが演算に混ざって結果を支配し得る bottomが伝播しやすい 1.0+の多くのトリガは「引数がbottomならbottom」を明示する。

3. 伝播ルール（MUGEN 1.0+ の核心）

3.1 原則：式中にbottomが出たら式全体がbottom

MUGEN 1.0+ では、bottomは「回復不能エラー値」として設計されており、 式のどこかでbottomが発生すると（原則）式全体がbottomになります。

3.2 Condition-type triggerではbottomを0扱い

trigger行の条件判定（Condition-type trigger）はbottomを0として扱うため、 「エラー式が真になって発火する」事故を避ける設計です。 その一方で、bottomの存在は「論理が曖昧/危険」なシグナルなので、デバッグ出力に警告が出るのが通常です。

3.3 例外：IfElse / Cond は“未採用分岐”のbottomを外へ出さない

IfElseとCondは、選ばれなかった分岐でbottomが出ても、返す分岐が正常ならbottomを外へ伝播させません。 ただし IfElseは3引数すべてを評価するため、未使用分岐でも0除算等の警告が出得ます。 Condは必要分岐だけ評価するため、危険式を評価そのものから回避できます。

4. 実機検証を仕様として読み解く

検証結果

  • 共通：WinMUGEN（旧）もMUGEN 1.0も、評価不能が起きると必ず警告テキストが表示された。
  • 共通：数値的な計算をしたらどちらも0になった。
  • 相違：DisplayToClipboardで%d表示すると、SFalseは0、bottomは(BOTTOM)と表示された。

4.1 「計算すると0」になるのは何を意味するか

SFalse（SC false）もbottomも、実運用では「安全側（発火しない側）に倒す」ため、 多くの文脈で 0（偽）相当として扱われます。 ただしMUGEN 1.0+では、bottomは単なる0ではなく “値としてのbottom” が残るため、 表示・デバッグ・伝播で差が出ます。

4.2 DisplayToClipboardの表示差が示すこと

%dでSFalseが0として表示されるのは「SFalseが0/1相当のSC値」であることと整合します。 一方、bottomが(BOTTOM)と表示されるのは、MUGEN 1.0+ がbottomを 「0に潰して隠す」のではなく、「評価不能の印（センチネル）として可視化」していることを示唆します。

4.3 検証用の最小テンプレ（例）

; -2 などで常時表示して比較する例（概念）
[State -2, Debug]
type = DisplayToClipboard
trigger1 = 1
text = "expr=%d"
params = <ここに検証したい式>

5. Ikemen GOではどうなるか（MUGEN互換の“落とし穴”）

Ikemen GOはMUGEN互換を掲げつつ拡張している一方で、互換差分（特に「エラー時の値扱い」）が残る場合があります。 代表的な報告として、無効リダイレクトがbottom相当にならず、0として比較に入ってしまうケースが挙げられています。 

; 問題が出た例（報告例）
trigger1 = helper(2519), rootdist x = [-75, 75]

; MUGEN側：helperが不在なら “bottom相当” で false 側に倒れる前提
; Ikemen側：無効リダイレクトが 0 扱いになり、0 が [-75,75] に入って true になり得る、という報告がある

この種の差分は、レンジ判定（interval演算）や「0が条件を満たしやすい比較式」で顕在化しやすく、 MUGENで“暗黙に安全”だったコードがIkemenで“逆に真になる”リスクを生みます。

6. 安全なコーディング指針（SFalse/bottomに依存しない）

6.1 必須：存在確認 → 参照（無効リダイレクトを踏まない）

; 推奨：存在確認を先に置く（MUGENでもIkemenでも事故率が下がる）
triggerall = NumHelper(2519) > 0
trigger1   = helper(2519), rootdist x = [-75, 75]

6.2 危険式はCondで“未評価化”する（MUGEN 1.0+ 的に最も筋が良い）

; helperがいる時だけ helper の life を参照し、いない時は自分の life にする
value = Cond(NumHelper(1234) > 0, (helper(1234), life), life)

6.3 「bottom/SFalseが偽になるから大丈夫」を設計原理にしない

  • 比較式の形（特に interval 判定）によっては、エンジン差で“0扱い”が真になり得る。
  • 警告が出ている時点で、将来の移植（Ikemen、別ビルド）や改修時に破綻しやすい。
  • 安全策（存在確認・Cond）で「危険式を踏まない」構造にするのが最も堅牢。

7. まとめ

  • SFalse：旧系の「SC false」。評価不能を“偽”として扱い、式評価を続けるための仕組み。
  • bottom：1.0+の「評価不能値」。式に出ると原則伝播。条件判定では0扱いで暴発防止。IfElse/Condが例外。
  • あなたの検証結果は、警告発生・数値文脈での0化・表示上のセンチネル差（SFalse=0、bottom=(BOTTOM)）を明確に示している。
  • Ikemen GOでは無効リダイレクトが0扱いで比較に入る報告があり、MUGEN前提コードが逆に真になるリスクがある。
  • 最終的な安全策は、存在確認→参照と、必要ならCondで未評価化（SFalse/bottomへの依存を断つ）。
